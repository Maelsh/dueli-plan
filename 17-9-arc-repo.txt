## 6. Lifecycle Duplication

**Actual relationship between `ScheduledTaskService` and `CronHandler`:**

`ScheduledTaskService` (`src/lib/services/ScheduledTaskService.ts`) is a **task processor** that:
- Schedules tasks (`schedule()`, `cancel()`)
- Processes pending tasks (`processPendingTasks()`)
- Executes task handlers (`executeTask()`)
- Implements Rule A (`handleAutoDelete`), Rule B (`handleScheduledNoOpponent`, `handleScheduledNotStarted`), Rule C (`handleAutoEnd`)
- Handles reminders, disconnection checks, aggregate recalculation, payout finalization

`CronHandler` (`src/lib/services/CronHandler.ts`) is a **cron trigger dispatcher** that:
- Dispatches Cloudflare Workers `scheduled` events by cron expression
- Calls `ScheduledTaskService.processPendingTasks()` for `* * * * *`
- Calls cleanup methods for `*/5 * * * *` and `0 * * * *` and `0 3 * * *`
- Contains a **separate** `handleLifecycleTimers()` function (lines 85–183) that **re-implements** Rule A, Rule B, and Rule C with **identical logic** but different SQL

**Concrete evidence of duplication:**

| Rule | ScheduledTaskService | CronHandler.handleLifecycleTimers |
|---|---|---|
| **Rule A** (Instant, 1hr no opponent) | `handleAutoDelete()` lines 151–229: SELECT competitions, DELETE requests/invitations/competition, FREE users, INSERT notifications | Lines 88–116: SELECT competitions with same WHERE, DELETE requests/invitations/competition, FREE users, INSERT notifications — **identical SQL patterns** |
| **Rule B** (Scheduled, 1hr post-schedule) | `handleScheduledNoOpponent()` lines 235–275 + `handleScheduledNotStarted()` lines 281–315 | Lines 118–149: SELECT competitions with same WHERE, UPDATE status='cancelled', FREE users, INSERT notifications — **identical SQL patterns** |
| **Rule C** (Live, 2hr max) | `handleAutoEnd()` lines 320–374 | Lines 151–182: SELECT competitions with same WHERE, UPDATE status='completed', FREE users, DELETE chunk_keys, INSERT notifications — **identical SQL patterns** |

**Key observation:** `ScheduledTaskService` already handles all three rules via its task queue. `CronHandler.handleLifecycleTimers()` bypasses the task queue entirely and runs the same logic directly. This is **behavioral duplication**, not merely different triggering. Both will fire for the same competitions if a `competition_scheduled_tasks` row exists AND the cron expression matches.

**Delegation:** `CronHandler.runMinuteMaintenance()` delegates to `ScheduledTaskService.processPendingTasks()`, but `handleLifecycleTimers()` does **not** delegate — it reimplements.

**Consolidation warranted:** Yes. The `handleLifecycleTimers()` function in `CronHandler` should be removed and its rules delegated to `ScheduledTaskService` (which already owns them). This is a clear **F-6 remediation candidate**.

## 7. OOP/MVC Boundary Findings

Only meaningful findings beyond the SQL/inline-model violations already documented:

1. **`AdminController.executeModerationAction()` (lines 213–274)** — This private method implements a mini service (ban_user, delete_comment, delete_competition) with cascade deletes inside the controller. It should be extracted to `ArbitrationService` or a dedicated `ModerationService`. The controller is orchestrating data mutations that belong in a service layer.

2. **`MatchmakingController` (entire file)** — The entire matchmaking algorithm (scoring, filtering, pagination) is implemented as raw SQL in the controller. There is no `MatchmakingModel` or `MatchmakingService`. This is the most substantial MVC violation after `AdminController`.

3. **`RecommendationController.getGuestRecommendations()` (lines 76–104)** — Guest recommendations bypass `RecommendationEngine` and execute raw SQL directly in the controller, while authenticated recommendations correctly use the service. This is an inconsistency in the same controller.

4. **`analytics/routes.ts` and `delete-account.ts`** — SQL is placed in route handlers (`routes.ts`) rather than in controllers or models. This bypasses both the controller orchestration layer and the model data-access layer.

## 8. Core-First Findings

**No Core-First violations found.**

- `src/models/` contains zero imports from `src/client/`, `src/modules/pages/`, or any presentation-layer module.
- `src/models/` imports only from `src/lib/services/` (business logic), `src/config/` (types), and `src/lib/errors/` (domain errors). No optional integration modules (advertisements, donations, payments, streaming) are imported by core models.
- `workers/dueli-realtime/` is a **separate Worker** (own `wrangler.toml`, own `package.json`). The core `src/` codebase has zero imports from it. `EventPusher` communicates via HTTP/Durable Objects, not via module imports.
- All optional integrations (advertisements, donations, payments, ad-blocks, ad-reports, earnings, withdrawals, transparency) are in separate `src/modules/api/*/routes.ts` files mounted in `main.ts`. They do not leak into core domain models.
- `main.ts` is strictly a wiring file — it imports and mounts routes but contains no business logic or SQL.

## 11. Negative Findings

Important items investigated that are **NOT violations**:

1. **`src/models/` OOP structure** — All 31 model classes properly extend `BaseModel<T>`. No model contains presentation concerns or client imports.
2. **`src/client/` SQL-free** — Client-side TypeScript contains zero database queries. The `SELECT/INSERT/UPDATE/DELETE` matches are HTTP method type strings.
3. **`src/modules/pages/` orchestration, not data-access** — Page modules (`profile-page.ts`, `settings-page.ts`, `admin-dashboard-page.ts`, etc.) generate HTML and embed client JS. They do not execute SQL except for the two documented cases in Section 4.
4. **`src/modules/api/*/routes.ts` pattern** — Route files delegate to controllers (e.g., `competitions/routes.ts`). The exceptions (`analytics`, `delete-account`, `ad-reports`, `search`) are violations, not the pattern itself.
5. **`EventPusher` → realtime worker** — `EventPusher` communicates with `workers/dueli-realtime/` via HTTP/Durable Objects, not via module imports. Core-First boundary is preserved.
6. **`NotificationModel` imports `NotificationPresenter`** — This is a service-layer import (`lib/services/`), not a presentation/client import. Legitimate.
7. **`console.error` / `console.log` in controllers and services** — These are developer diagnostics, not user-visible text. Not i18n violations.
8. **Migration SQL in `migrations/`** — Schema definitions are exempt from MVC/i18n rules.
9. **`ScheduledTaskService` task scheduling from controllers** — Controllers calling `taskService.schedule()` is legitimate orchestration; the violation is the duplicate lifecycle logic in `CronHandler`, not the scheduling itself.
