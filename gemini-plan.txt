4. فجوة الـ Backend المغلق مقابل المنتج غير المكتمل
أحد أهم أسباب وصول المشروع لهذه الحالة هو «الوهم البرمجي» الناتج عن قياس الإنجاز باختبارات الوحدة (Unit Tests) واكتمال مسارات الـ HTTP status code 200 في الخادم الخلفي.
4.1 تفكك العقود (Contract Mismatch) كقضية بنيوية
الخادم الخلفي يعتمد معيار استجابة عام:
code
TypeScript
// BaseController.ts
protected success<T>(c: Context, data: T, status: StatusCode = 200) {
    return c.json({ success: true, data }, status);
}
وعند استدعاء controller.getConversations(c):
code
TypeScript
// MessageController.ts
return this.success(c, { conversations });
// الاستجابة تصبح: { success: true, data: { conversations: [ ... ] } }
بينما الواجهة الأمامية كُتبت بافتراض:
code
JavaScript
// messages-page.ts
const data = await res.json();
if (data.success && data.data?.length > 0) {
    container.innerHTML = data.data.map(...) // data.data كائن وليس مصفوفة!
}
النتيجة الميدانية: الخادم يعطي 200 OK، واختبارات التكامل على الخادم تنجح، لكن المستخدم يرى شاشة رمادية ميتة لا تحتوي على رسائل.
4.2 الفشل الصامت (Silent Failure) وغياب المعالج المركزي
لا يوجد في الواجهة الأمامية Global Error Handler أو Fetch Interceptor.
عند ورود خطأ 401 Unauthorized أو 500 Internal Server Error، ينتهي الكود في أغلب الصفحات بـ catch(e) { console.error(e); } دون إشعار المستخدم، أو ترك الـ Spinner يدور للأبد (#mainContent في الصفحة الرئيسية).
4.3 الاستنتاج المعماري
الـ Backend مكتمل بنسبة 85% وفق المنطق الداخلي، لكنه معزول تماماً عن كود الواجهة، مما يجعل الجاهزية الحقيقية للمنتج لا تتجاوز 32%.

6. معضلة البث المباشر و WebRTC
يعتبر البث المباشر المزدوج (Host vs Guest) العمود الفقري لمنصة Dueli. الفحص الميداني للكود يوضح أزمة حقيقية في هذه المنظومة:
6.1 الازدواجية الخطيرة في كود الـ WebRTC
يوجد في المستودع ملفان مستقلان تماماً لإدارة الاتصال:
src/client/services/P2PConnection.ts (403 أسطر): يعتمد على RTCPeerConnection المحلي ويرتبط بـ LiveRoom.ts.
src/lib/services/P2PConnection.ts (576 أسطر): نسخة ثانية ومحدثة تدعم المحاولات المتكررة وحساب الـ Latency وجودة الاتصال، لكنها غير مستوردة وغير مستخدمة في أي مكان في المشروع نهائياً!

6.3 معضلة خوادم الـ TURN والشبكات المقيدة
الكود يدعم افتراضياً خوادم STUN المجانية (stun:stun.l.google.com:19302).
في شبكات الهاتف المحمول في الشرق الأوسط (مثل شبكات 4G/5G في مصر والخليج وNorth Africa)، تفشل اتصالات P2P المباشرة خلف الـ Symmetric NAT بنسبة تتجاوز 40% ما لم يتوفر خادم TURN حقيقي.
في .dev.vars.example، تم وضع متغيرات TURN_URL و TURN_SECRET و TURN_API_TOKEN، ولكن في بيئة الإنتاج الحالية لم يتم ربط خادم TURN مدفوع أو تشغيل coturn حقيقي، مما يتسبب في تعليق البث في حالة "Connecting..." بشكل متكرر.
6.4 مركب الفيديو (Compositor) ورفع المقاطع
VideoCompositor.ts يقوم بدمج بث الفيديو في المتصفح باستخدام <canvas> قبل الإرسال لخادم FFMPEG. هذه العملية تستهلك 80-100% من وحدة المعالجة المركزية (CPU) على أجهزة الموبايل الضعيفة، مما يؤدي إلى سقوط الإطارات (Dropped Frames) وارتفاع حرارة الأجهزة.
7. التقييم، التفاعل الاجتماعي، والتوصيات
7.1 فوضى محركات التوصية (Recommendation Architecture Chaos)
تم اكتشاف 3 تطبيقات متوازية ومتضاربة لمحرك التوصيات داخل المشروع:
المحرك الخادمي الأصلي (src/lib/services/RecommendationEngine.ts):
يعتمد أوزاناً دقيقة: اللغة (25)، البلد (20)، الفئة (20)، عدم المشاهدة (10)، الحداثة (10)، التقييم (15)، والمتابعة (15).
محرك الواجهة الأمامية (src/client/helpers/RecommendationEngine.ts):
يقوم بعملية حساب أوزان مستقلة في المتصفح ويخزن النتائج محلياً في localStorage.getItem('dueli_recommendations')، متجاوزاً منطق الخادم!
محرك المطابقة اللحظي (src/controllers/MatchmakingController.ts):
يستخدم استعلام SQL هجين ومستقل تماماً لحساب التوافق:

9. البيانات التخليقية (Synthetic / Demo Data Lifecycle)
9.1 الوضع الحالي المعتمد (D2 Closure)
تم بناء SyntheticRetirementService.ts لحماية قاعدة البيانات من حذف مستخدمين لديهم ارتباطات أجنبية (Foreign Keys).

الاستدعاء يتم بشكل فردي (Retire One) عند تسجيل مستخدم جديد أو إنشاء مسابقة حقيقية.
9.2 نقطة الاختناق المكتشفة في الكود (The Retirement Bottleneck)
في db/seed.sql، جميع المستخدمين التخليقيين تقريباً لديهم علاقات مسجلة (تعليقات، تقييمات، متابعات، إشعارات، مسابقات تجريبية).
دالة hasDependent(...) تفحص الجداول وترى وجود هذه العلاقات، وبالتالي تعيد true دائماً!
النتيجة الحقيقية: دالة التقاعد تتجاوز هؤلاء المستخدمين ولا تستطيع حذفهم، مما يبقي البيانات التجريبية محبوسة في الإنتاج دون تنظيف فعلي!
9.3 المقترح المعماري: دورة حياة البيانات التخليقية (Synthetic Lifecycle 2.0)
بدلاً من محاولة الحذف الفيزيائي الصارم (HARD DELETE) الذي يهدد سلامة القيود المرجعية، يجب الانتقال إلى:
العزل المنطقي (Soft Archival): إضافة حقل lifecycle_status ('active' | 'graduated' | 'dormant' | 'archived') في جدولي users و competitions.
الحجب التلقائي عن الواجهات الحية: استثناء أي سجل يحمل is_fake = 1 من واجهات الصفحة الرئيسية وقوائم المتصدرين والبحث بمجرد تجاوز عدد المستخدمين الحقيقيين عتبة محددة (Threshold: مثلاً 500 مستخدم حقيقي).
مهمة صيانة مجدولة (Scheduled Pruning Worker): فك الارتباطات التخليقية البينية (Synthetic-to-Synthetic) بأمان وأرشفة السجلات دون كسر سلامة الـ Foreign Keys.

شروط العبور: التحقق من عدم ظهور أي حساب يحمل وسم Demo في نتائج البحث الرسمية للمستخدمين الحقيقيين عند تفعيل وضع الإنتاج.

شروط العبور: إجراء عملية تبرع تجريبية، تسجيل أرباح، تقديم طلب سحب، واعتماده من لوحة الإدارة مع تسجيل الحركة في الـ Ledger.

إلغاء كود إخفاء المساعدة للمسجلين، وإنشاء صفحة الأسئلة الشائعة (FAQ) وشرح قوانين التنافس ونقاط التقييم.
شروط العبور: ظهور أيقونة المساعدة لكافة المستخدمين، ووجود روابط فعالة لشروط الخدمة والخصوصية في الفوتر.

17. Browser/Product Validation Matrix
تحديد السيناريوهات الميدانية الكاملة التي يجب أن تتحول إلى اختبارات قبول متصفح (E2E Scenarios عبر Playwright):
المعرف	السيناريو الميداني (User Journey)	خطوات التحقق بالمحاكاة الكاملة للمتصفح	معيار النجاح الصارم
E2E-01	رحلة إنشاء الحساب وتجهيز الهوية	تسجيل مستخدم جديد عبر البريد أو الـ OAuth ← ضبط الاسم والبلد واللغة ← رفع صورة شخصية ← الانتقال للملف الشخصي.	ظهور وسم التوثيق والاسم بشكل سليم، وتواجد زر "تعديل الملف" مباشرة دون تحديث الصفحة.
E2E-02	رحلة التحدي وإنشاء المسابقة ودعوة المنافس	المستخدم A ينشئ مسابقة في تصنيف "حوار" ← يفتح لوحة الدعوة ← يختار المنافس B المتصل ← يستقبل B إشعاراً فورياً ويوافق ← يتم نقلهما لغرفة البث.	إنشاء السجل، وصول إشعار Web Push/Realtime، ودخول الغرفة دون أخطاء 404 أو تعليق.
E2E-03	رحلة البث المباشر المتطابق والجمهور	انضمام المتنافسين A و B للغرفة ← تشغيل الكاميرا والميكروفون ← إنشاء اتصال P2P ← انضمام المشاهد C ← بدء العد التنازلي.	تدفق الفيديو في الشاشتين المتقابلتين، ظهور عدد المشاهدين (1)، وسماع الصوت بوضوح.
E2E-04	رحلة التفاعل والتقييم اللحظي	المشاهد C يقوم بالتصويت وإعطاء تقييم 4 نجوم للمتسابق A ← كتابة تعليق في الدردشة الحية ← إرسال تبرع تجريبي عبر البطاقة.	ظهور التوست بنجاح، تحديث متوسط تقييم المتسابق، وظهور التعليق فورياً في شريط المحادثة.
E2E-05	رحلة إغلاق المسابقة وإعلان الفائز	انتهاء وقت الجولة ← إغلاق التصويت آلياً ← حساب مجموع نقاط الحكام والجمهور ← إعلان الفائز وتحديث رصيد الأرباح.	تحول حالة المسابقة إلى recorded، تسجيل النقاط في قاعدة البيانات، وإيداع حصة الفوز في Ledger.
E2E-06	رحلة المحفظة وطلب السحب المالي	المتسابق الفائز يدخل صفحة الأرباح ← يستعرض الرصيد المتاح وتفاصيل العمليات ← يقدم طلب سحب بقيمة 50$ مع تحديد وسيلة السحب.	قراءة الجلسة بالتوكن الصحيح، انتقال المبلغ إلى hold في دفتر الأستاذ، وظهور الطلب في جدول السحوبات.
E2E-07	رحلة الإدارة والرقابة والموافقة	تسجيل دخول المشرف بصفة SuperAdmin ← فتح لوحة الإدارة ← مراجعة طلب السحب المعلق ← إدخال رقم الحوالة واعتماد الصرف.	تحميل لوحة الإدارة بدون حظر، نجاح تحديث السجل إلى paid، وتسجيل الحركة في admin_audit_logs.
E2E-08	رحلة المحادثات الخاصة (Direct Messaging)	المستخدم A يفتح بروفايل B ← يضغط "إرسال رسالة" ← كتابة رسالة نصية ← يفتح B صفحة الرسائل ويرد على A.	تفكيك كائن المحادثات بنجاح، عدم ظهور شاشة بيضاء، وتحديث قائمة المحادثات في الوقت الفعلي.
18. استراتيجية التنفيذ: كيف سنعمل من الآن فصاعداً؟
لضمان عدم تكرار الأخطاء السابقة، يجب تطبيق بروتوكول ضبط الجودة الصارم:
18.1 قاعدة «عدم العودة للماضي إلا بدليل»
لا يتم المساس بكود الـ Backend Debt المغلق (C1–C7, D1–D3, N-2) نهائياً، إلا إذا أثبت اختبار متصفح حقيقي وجود خلل أو تعارض في هذا الكود حصراً.
18.2 بروتوكول التنفيذ: الوكيل المحلي مقابل الوكيل المستقل (Local ↔ Remote)
🟦 LOCAL Agent:
يتولى بوابة واحدة (Gate) أو بنداً وظيفياً محدداً.
يكتب الاختبار الفاشل أولاً (Red Test).
يجري الإصلاح البرمجي المطلوب.
يختبر الإصلاح في المتصفح المحلي ويحدث WORKLOG.md و PLAN-STATUS.md.
يفتح فرعاً مستقلاً (Branch) ويرفع Pull Request.
🟧 REMOTE Agent:
يستنسخ الفرع في بيئة معزولة ونظيفة.
يشغل اختبارات المتصفح المؤتمتة.
لا يملك صلاحية تعديل الكود؛ دوره هو المراجعة المستقلة فقط (APPROVE أو REJECT).
لا يتم دمج أي PR في فرع main إلا بعد صدور APPROVE الصريح.
18.3 دورة حياة الفرع والـ PR المنضبط
كل PR يمثل نتيجة مستخدم ملموسة واحدة (One User Outcome).
عناوين الالتزام تتبع المعيار الدقيق: fix(core): ... أو feat(core): ....
يمنع منعاً باتاً دمج تغييرات بنية عامة (Refactor) أو تغيير حزم الـ CI ضمن مهام إصلاح الواجهات.
19. المكاسب السريعة مقابل الإصلاحات العميقة (Quick Wins vs Deep Architecture)
لتحقيق تقدم سريع وملموس يرفع الروح المعنوية ويعيد تشغيل المنصة في غضون أيام قليلة، يتم فرز المهام إلى مسارين:
19.1 المكاسب السريعة (Quick Wins — تنجز خلال 48 إلى 72 ساعة)
تصحيح مفتاح الجلسة (sessionId): استبدال استدعاءات session_id بالدالة الموحدة يحيي فوراً: لوحة الإدارة، صفحة الأرباح، بوابة المعلن، وتتبع الشكاوى.
سد ثغرة الـ XSS في صفحة الاستكشاف: تعديل سطر واحد في explore-page.ts يغلق أخطر ثغرة أمنية حاجبة في الواجهة.
تصحيح عقد الرسائل (messages-page.ts): تعديل قراءة data.data.conversations يعيد المراسلة الفورية للعمل فوراً.
تعريف دالة showToast في صفحة المسابقات: يمنع الانهيار البرمجي أثناء التقييم والتذكير.
توقيت تحميل البروفايل (profile-page.ts): ربط updateProfileActions بوعد checkAuth().then(...) يعيد إظهار أزرار الإجراءات والمتابعة.
استكمال الـ 21 مفتاحاً في ar.ts: يمنع تسرب النصوص الخام لتصنيفات المسابقات.
إلغاء حجب أيقونة المساعدة للمسجلين: تعديل سطر في AuthService.ts يعيد إتاحة المساعدة لجميع المستخدمين.
19.2 الإصلاحات العميقة (Deep Architecture — تتطلب تخطيطاً وتنفيذاً متأنياً)
تأمين خادم TURN مخصص: تجهيز VPS مستقل عليه coturn أو الاشتراك في Cloudflare Calls لضمان موثوقية البث المباشر.
إعادة هيكلة محرك التوصيات: شطب محرك المتصفح وتوحيد الحسابات الخادمية.
أتمتة دورة حياة البيانات التخليقية: بناء منطق الأرشفة الذاتية (Soft Archival).
تأسيس الصياغة القانونية وشروط الخدمة: وضع وثائق قانونية واضحة وشاملة لمنع النزاعات.
بناء وضع التلفاز والشاشات الكبيرة (Arena TV View): تصميم واجهة مخصصة للعرض السينمائي المريح.
20. الأسئلة والقرارات المطلوبة من قيادة المشروع
لتثبيت وثيقة الـ Master Roadmap نهائياً والبدء في التنفيذ الفوري، نطلب من قيادة مشروع Dueli حسم القرارات الإدارية والتنظيمية الستة التالية:
القرار 1: الهيكل المالي وبوابات الدفع والسحب
هل يستمر المشروع في مرحلة الـ Beta بالاعتماد على مسار الصرف اليدوي بواسطة الأدمن (Manual Admin Payout) مع توثيق التحويل في سجلات المنصة، أم ترغب القيادة في دمج بوابة صرف آلية (مثل Stripe Connect أو بوابات محلية) قبل الإطلاق العام؟
التوصية المعمارية: الاستمرار في الصرف اليدوي لمرحلة الـ Beta لتقليل التعقيد والتكاليف، مع تحسين واجهة إدخال وتأكيد الحوالة للأدمن.
القرار 2: توفير خادم WebRTC Relay (TURN Server)
هل توافق القيادة على توفير خادم TURN مدفوع (مثل خادم VPS بتكلفة ~$10 شهرياً لتشغيل coturn، أو شحن رصيد Cloudflare Calls) لضمان عدم فشل البث المباشر في الدول العربية وشبكات الـ 4G/5G؟
التوصية المعمارية: لا يمكن إطلاق ميزة البث المباشر بدون خادم TURN مخصص، والاعتماد على STUN المجاني هو مجازفة مباشرة بانهيار البث للمستخدمين.
القرار 3: خدمة إرسال البريد الإلكتروني (Transaction Emails)
يستخدم المشروع حالياً سكربت PHP مخصص على خادم iFastNet لإرسال رسائل التحقق واستعادة كلمة المرور، وهو معرض للتعطل ووصول الرسائل لملفات الـ Spam. هل يتم استبداله بمزود سحابي معتمد (مثل Resend أو SendGrid أو Postmark)؟
التوصية المعمارية: الانتقال الفوري إلى Resend لضمان تسليم رسائل التحقق وسرعة وصولها للمستخدمين.
القرار 4: مصير صفحات الاختبار المكشوفة في البث (/live/host, etc.)
هل نوافق فوراً على إغلاق مسارات الاختبار التجريبية وعزلها عن الإنتاج واقتصار البث على المسار الرسمي للمسابقة /live/:id؟
التوصية المعمارية: الموافقة الفورية لحماية سمعة المنصة وأمانها في محركات البحث.
القرار 5: سياسة تنظيف البيانات التخليقية (Demo Data)
هل تعتمد القيادة سياسة العزل المنطقي (Soft Archival) للبيانات التجريبية القديمة بدلاً من محاولة الحذف الفيزيائي الصارم الذي يعطل قواعد البيانات بسبب قيود الـ Foreign Keys؟
التوصية المعمارية: اعتماد العزل المنطقي وحجب وسم Demo آلياً فور توفر المتسابقين الحقيقيين.
القرار 6: التراخيص والكيان القانوني
هل تملك المنصة صيغة معتمدة لشروط الخدمة وسياسة النزاهة وحقوق الملكية، أم نقوم بصياغة مسودة قانونية احترافية قياسية متوافقة مع منصات التنافس وصناع المحتوى ودمجها في المنصة؟
التوصية المعمارية: صياغة مسودة شروط خدمة قياسية احترافية باللغتين العربية والإنجليزية ودمجها ضمن البوابة [G9].
الخلاصة المعمارية والخطوة التالية
لقد انتهت مرحلة "الترقيعات المتفرقة" وأصبح أمامنا خريطة طريق واضحة ومبنية على الأدلة الصريحة من الكود.
بمجرد اعتماد هذا التقرير وتأكيد القرارات الستة المطلوبة أعلاه، سنبدأ فوراً في تفعيل البوابة [G0] ثم الانتقال للمكاسب السريعة في [G1] و [G2] و [G3] بنظام العمل المعتمد (LOCAL ↔ REMOTE)، لنحول Dueli من مشروع يعاني من أعطاب خفية إلى منصة مسابقات اجتماعية مكتملة، مستقرة، وآمنة تليق بتطلعات الفريق والمستخدمين.
