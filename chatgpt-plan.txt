# 4. Proven Frontend Gaps Still Present

## 4.1 S0 — Reflected XSS

هذا ليس مجرد finding تاريخي.

في `src/modules/pages/explore-page.ts` ما زال هناك:

`searchQueryDisplay.innerHTML = ... ${search} ...`

أي أن query parameter يدخل مباشرة إلى HTML.

هذا يثبت أن W0.1 من خطة الـFrontend **لم يُغلق بعد**.

**Classification: G — Broken / Security Risk**

**Priority: BLOCKER**

## 4.2 S0 — Session Key Duplication

ما زال الكود الحالي يحتوي على:

`localStorage.getItem('session_id')`

في صفحات منها:

* advertiser portal
* complaint tracking
* earnings
* live finance
* admin.

بينما بقية النظام يستخدم `sessionId`.

مثلاً advertiser portal ما زال يقرأ `session_id`.

والـroadmap نفسه يحدد هذا كتعدد مصدر حقيقة لنفس الجلسة.

**Classification: G — Broken / Architecture Inconsistency**

والأهم:

هذا ليس Bug واحداً.

إنه **contract-level frontend infrastructure defect** يؤثر عدة flows.

# 7. Banking / Stripe — Finding مهم جداً

بحثت في الوضع الحالي لـStripe، وليس في افتراضات قديمة.

Stripe حالياً لا يدرج **Egypt** ضمن قائمة الدول المدعومة لفتح حساب Stripe تقليدي لاستقبال المدفوعات.

وفي المقابل، Stripe تعرض Egypt ضمن Global Payouts مع EGP عبر SWIFT كقدرة مستقبلية مدرجة لـH2 2027، وليست حلاً حالياً لحساب Stripe مصري تقليدي.

كما أن فتح Stripe في دولة أخرى يتطلب entity قانونية وtax ID وموقعاً فعلياً وحساباً بنكياً فعلياً في تلك الدولة وغيرها.

لذلك:

**لا يجوز أن نضع "Stripe Connect" كحل نهائي في الـRoadmap قبل قرار مالك المشروع عن الكيان القانوني/الدولة التي ستملك حساب Stripe.**

### Current classification

**H — External Dependency**

والقرارات المطلوبة:

1. أين الكيان القانوني الذي سيشغّل Dueli؟
2. أين حساب Stripe؟
3. أين الحساب البنكي الذي يستقبل settlement؟
4. هل المنافسون سيكونون connected accounts؟
5. كيف سيتم payout لهم؟
6. ما الدولة/الدول التي يسمح بها الهيكل القانوني الفعلي؟

هذا **Project Owner + Legal + Operational Decision**، وليس Coding Task.

# 18. i18n

Backend i18n architecture is mature enough that new keys are generally handled in ar/en together.

However the Frontend historical audit found numerous localization issues, and current code still contains English fallback literals such as:

`'Messages'`, `'Loading...'`, `'No conversations yet'`.

That does not prove every fallback is user-visible in every path, but it proves the rule:

> Complete UX localization

has not yet been mechanically enforced everywhere.

**Classification: C**

The future Gate must test the rendered UI, not just compare dictionaries.

# 21. Security

The security program has substantially improved.

C1–C6 are now represented in the current main history.

However the current product still has a directly proven frontend security defect:

**reflected XSS in `/explore?search=`.**

That means:

> Backend Security Closure ≠ Product Security Closure.

This is exactly why the new Master program must contain a **Product Security Regression Gate** without reopening the entire old Backend Gate.

# 22. Architecture Coherence

The strongest architecture problems found so far are:

### A

Backend + client RecommendationEngine duplication.

### B

`sessionId` vs `session_id`.

### C

Historical documentation/plans vs current implementation.

### D

Multiple realtime paths:

* SSE production
* WebRTC signaling
* optional DO/WS future.

### E

Frontend pages contain substantial inline application logic.

This does not automatically mean a rewrite is justified.

The correct strategy is:

**contract consolidation before structural refactoring.**
