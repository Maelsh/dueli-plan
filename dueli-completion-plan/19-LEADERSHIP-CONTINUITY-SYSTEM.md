## 1. الهدف والمبدأ

استمرارية Dueli لا تعتمد على ذاكرة محادثة أو وكيل واحد أو نافذة واحدة أو بقاء أداة بعينها متاحة. المستودعات هي سجل العمل المشترك القابل للتدقيق؛ الأشخاص والوكلاء يستطيعون استعادة السياق من الأدلة وإعادة تقييم الأدوار عند الحاجة.

هذا المستند يضيف طبقة استمرارية ولا يستبدل المصادر القائمة:
- **14** هو المصدر الوحيد لترتيب الوحدات والحالة وCanonical NEXT.
- **08** هو مصدر قرارات المالك وسياسات المنتج.
- **10** هو بروتوكول LOCAL → تحقق القائد/GitHub → REMOTE → merge → بوابات ما بعد الدمج.
- مواصفات الوحدة في **05/12/13/15/18** والملفات الحاكمة في مستودع الكود تبقى ملزمة.
- لا يُعد أي ملخص محادثة أو تقرير وكيل بديلاً عن التحقق من GitHub. يسجل التقرير ما فُحص ومتى وعلى أي SHA.

## 2. الأدوار والصلاحيات عند الاستعادة

- **مالك المشروع:** صاحب القرار النهائي في المنتج والسياسة والأولوية والنطاق والإجراءات الواقعية المحجوزة له.
- **قائد التخطيط:** يحلل المتطلبات ويقترح موضعها في المسار الموحد ويحافظ على اتساق الخطة. لا يغيّر الكود ولا يدمج PR الكود.
- **القائد التقني والتنفيذي / Merge Owner:** يثبت الحالة، يصدر التكليفات، يتحقق من الأدلة، ينسق REMOTE، ويُجري دمج الكود بعد الموافقة المستقلة الصريحة واجتياز البوابات. يحدّث الخطة عبر PR وفق التفويض القائم.
- **LOCAL / الوكيل التنفيذي:** ينفذ النطاق المحدد، يجمع الأدلة ويحدّث WORKLOG.md وPLAN-STATUS.md داخل PR الكود. لا يدمج ولا ينشر ولا يوسّع النطاق من تلقاء نفسه.
- **REMOTE / المراجع المستقل:** يراجع التغيير على exact HEAD/BASE ويصدر حكمًا صريحًا. لا ينفذ ولا يدمج ولا يتخذ قرارات نطاق.
- **أي بديل يتولى دورًا:** لا يفترض أنه ورث ذاكرة سلفه. يستعيد الدور من هذا المستند ومن الحالة الحية، ويتحقق من صلاحياته الفعلية، ويعلن ما استطاع وما تعذر إثباته.

إذا تعذّر وجود المالك، يستمر العمل الموثق وغير المتعارض الذي يقع ضمن تفويض سابق صريح؛ لا يتخذ أي بديل قرارات منتج/سياسة/مال/إنتاج محجوزة للمالك. تحفظ المسألة كقرار معلق ويستمر فقط ما لا يعتمد عليها.

## 3. ترتيب استعادة القيادة — إلزامي لكل نافذة جديدة أو بديل

1. اقرأ هذا المستند، ثم 14 و04 و08 و10 و11، ثم المواصفة المرتبطة بـNEXT؛ اقرأ تقرير التخطيط الأحدث إذا كان متعلقًا بالمهمة.
2. اقرأ من CODE repo: AGENTS.md وWORKLOG.md وPLAN-STATUS.md والوثائق الحاكمة ذات الصلة، بما فيها docs/01 وdocs/11 وdocs/12 وdocs/13 وdocs/18 حيث توجد وتنطبق.
3. افحص المستودعين مباشرة: main SHA الحالي في CODE وPLAN، وPRs المفتوحة/النشطة، والرؤوس والفروع والـreviews والـchecks والـworkflow runs ذات الصلة. لا تفترض أن SHA المذكور في تسليم قديم ما زال HEAD.
4. طابق سجل الخطة مع أحداث GitHub اللاحقة. سجّل الاختلافات، ولا تصلح التناقض بصمت ولا تعاود تكليف PR نشطة.
5. حدد الحالة الحالية، وCanonical NEXT من 14، والـblockers، والبوابات المطلوبة. لا تعِد اختبار أو فتح عمل مغلق إلا عند وجود عيب جديد مثبت.
6. أرسل للمالك لقطة استئناف قصيرة: SHA الحالية، ما ثبت مباشرة، ما هو منقول من سجل سابق، ما لم يثبت، القرار/الخطوة التالية. ثم تابع بروتوكول 10.

## 4. «ملخص استعادة القيادة» الإلزامي في تقارير LOCAL

يضيف LOCAL في نهاية كل تقرير تسليم، بما فيه تقارير remediation وتقرير ما قبل المراجعة، قسمًا بهذه البنية. يجب أن يكون محددًا ومحدّثًا لا قالبًا عامًا:

- **ROLE REMINDER:** LOCAL منفذ فقط؛ القائد يراجع وينسق؛ REMOTE يراجع استقلاليًا؛ المالك يملك قرارات المنتج.
- **UNIT / PLAN:** رقم الوحدة واسمها، رابط 14/المواصفة، PLAN SHA وCanonical NEXT كما قرئَا.
- **CODE IDENTITY:** CODE main SHA وقت التكليف، BASE، PR، HEAD النهائي، ورابط commit/PR.
- **STATE:** ما اكتمل فعلًا (LOCAL/CI/REMOTE/merge/deploy/acceptance) وما لم يكتمل. لا تستخدم DONE/DEPLOYED/PROD VERIFIED بلا دليل لكل حالة.
- **EVIDENCE:** الروابط المحددة للاختبارات والـchecks والمراجعة والـruns؛ لكل دليل SHA ونتيجة. أرفق التقرير الكامل في المستودع عند الحاجة بدل إغراق المحادثة.
- **BLOCKERS / LIMITS:** المخاطر، الاختبارات غير المنفذة، الأدلة المتعارضة، وما يحتاج قرار مالك.
- **NEXT:** خطوة واحدة تالية وفق 14، ومن المسؤول عنها، وما بوابتها.
- **RECOVERY NOTE:** ما يجب أن يعرفه قائد جديد ليستأنف دون سؤال LOCAL لإعادة سرد المشروع، بما في ذلك أي تقرير REMOTE قائم والرأس الذي يغطيه.

إذا تعذر التحقق من أي حقل، اكتب UNKNOWN/NOT VERIFIED وسبب ذلك؛ لا تخمّن ولا تخفِ الفجوة.

## 5. قوالب التكليفات والتسليم

### 5.1 بطاقة LOCAL قبل التنفيذ

يصدر القائد تكليفًا مستقلًا بذاته يتضمن:
- CODE repo وPLAN repo وروابط الملفات المحددة وPLAN SHA.
- UNIT/موضعها في 14 وCanonical NEXT، وCODE main SHA وBASE اللذين تحقّق منهما لحظة التكليف.
- المشكلة المرصودة والأدلة المتاحة، ونطاق العمل وDoD والاختبارات المطلوبة.
- القيود والملفات التي لا يجوز لمسها، التبعيات، نوع التحقق T/B/S/H، وما يتطلب موافقة المالك.
- وجوب قراءة AGENTS.md والوثائق الحاكمة وتحديث WORKLOG.md وPLAN-STATUS.md داخل PR.
- المطلوب من التقرير وملخص استعادة القيادة في §4.
- لا merge ولا deploy ولا production write من LOCAL.

### 5.2 تكليف REMOTE بعد اكتمال LOCAL فقط

قبل إرسال الموجه، يتحقق القائد من PR الفعلية وHEAD وBASE وdiff والـchecks المكتملة على HEAD المقصود. يرسل للمراجع:
- رابط PR، exact HEAD SHA، BASE SHA، candidate SHA إن كان مختلفًا، وروابط checks ذات الصلة.
- نطاق المراجعة ومعايير القبول والمخاطر المعروفة والملفات المتغيرة.
- طلب verdict نهائي صريح **APPROVE أو REJECT**، مع blockers وأدلة محددة، وتأكيد SHA الذي يغطيه الحكم.
- تذكير بأن المراجع لا يغيّر الكود ولا يدمج، وأن أي تغيير بعد المراجعة يبطل الموافقة على الرأس السابق.
- لا يصدر موجه REMOTE قبل تسليم LOCAL والتحقق من GitHub وفق 10.

### 5.3 بعد APPROVE والدمج

القائد وحده يتحقق من أن REMOTE وافق على exact HEAD وأن الـchecks المطلوبة خضراء، ثم يدمج مع expected_head_sha. بعد ذلك:
1. اقرأ merge result وCODE main والـactual merge SHA من GitHub.
2. تحقق من Post-merge Quality Gate وDeploy على **actual merge SHA نفسه**، مع الروابط والنتائج.
3. افصل الحالات: MERGED، POST-MERGE BLOCKED، CODE DONE، DEPLOYED، PROD VERIFIED، ACCEPTED/HUMAN DONE.
4. حدّث 14 و04 وأي وثائق لازمة عبر PR التخطيط، واحفظ حدود الأدلة والاختبارات غير المنفذة.
5. لا تبدأ الوحدة التالية حتى تُحسم بوابات ما بعد الدمج المطلوبة؛ الفشل يوقف دمج الميزات التالية وفق 10.

### 5.4 قالب التقرير بعد الدمج

يتضمن: PR وapproved HEAD وactual merge SHA، Quality run/result/SHA، Deploy run/environment/result/SHA، الحالة الدقيقة، ما لم يُختبر، plan PR/merge SHA، وCanonical NEXT الجديد. لا تكفي عبارة «تم الدمج» أو «CI أخضر».

## 6. التعامل مع نفاد الأدوات أو تعذر GitHub أو انقطاع السياق

### إذا تعذرت أداة GitHub أو انتهى رصيد الأدوات
- لا تدّعِ فحصًا مباشرًا، ولا تعتمد على نتائج مخزنة باعتبارها حية.
- أوقف الأفعال التي تتطلب تحققًا أو كتابة لا يمكن تأكيدها: لا merge، ولا deploy، ولا إغلاق blocker، ولا تكليف REMOTE على HEAD غير مثبت.
- اطلب من LOCAL أو المالك أو قائد التخطيط تزويدك بروابط GitHub/النصوص الدقيقة: main SHAs، PR/HEAD/BASE، review verdict، check names/run IDs/conclusions، merge SHA، deploy run، ولقطة 14/04. يجب أن تكون الأدلة قابلة للتحقق وليست مجرد قول «نجح».
- ميّز في الرد بين **VERIFIED DIRECTLY** و**REPORTED / EVIDENCE PROVIDED** و**NOT VERIFIED**.
- يمكن متابعة التخطيط أو صياغة تكليف لا يترتب عليه فعل غير قابل للتحقق، بشرط وسمه بوضوح بأنه غير منفذ/غير معتمد بعد.
- عند عودة الأدوات، أعد التحقق من الحالة الحية قبل أي إجراء حساس، وطابق الأدلة المقدمة مع GitHub.

### إذا انتهت نافذة المحادثة أو تغير القائد
- يبدأ البديل من §3، لا من آخر رسالة أو الذاكرة التلقائية.
- لا يكرر الأعمال المغلقة؛ يتحقق من HEAD والـPR النشطة أولًا.
- إذا لم يستطع إثبات هوية الرأس أو صلاحية التفويض، يتوقف عن الدمج/النشر ويطلب دليلًا أو تفويضًا محددًا.
- لا يحاول تخمين ما كان «المقصود» من حالة متناقضة؛ يوثق التعارض ويستخدم أحدث حدث GitHub مؤكد مع احترام 14.

### إذا تعذر وجود المالك
- تظل قرارات 08 المعتمدة نافذة. لا تُستحدث سياسة أو توسعة نطاق أو إجراء إنتاجي/مالي محجوز.
- يمكن مواصلة مهام تقنية سبق اعتماد نطاقها وتفويضها ولا تعتمد على قرار جديد.
- أي قرار منتج جديد أو مخاطرة خارج التفويض يبقى OWNER DECISION REQUIRED، ويُحفظ في الخطة.

## 7. دورة التعلم والتحسين

بعد كل حادثة أو رفض REMOTE أو فشل CI/Deploy أو اختلاف بين الخطة والكود:
1. سجل الواقعة والأدلة والـSHA والتوقيت في WORKLOG/PLAN-STATUS أو سجل الوحدة المناسب.
2. افصل **السبب المثبت** عن الفرضية، والأثر عن الرأي، والـblocker عن التحسين غير الحاجب.
3. استخرج قاعدة عملية تمنع تكرار الخطأ، وحدد الملف الحاكم الذي يجب تحديثه (10 للبروتوكول، 02 لموجه القائد، 14 للحالة/التسلسل، 08 لقرار المالك، أو مواصفة الوحدة).
4. لا تغيّر قاعدة أو سياسة منتج من حادثة منفردة دون صلاحية؛ قرار المنتج يعود للمالك، وتعديل ترتيب الخطة يمر عبر المسار المعتمد.
5. أضف روابط PR/commit/runs، ولا تكتفِ بملخص داخل المحادثة.
6. مراجعة دورية عند كل handoff كبير، وكل إغلاق وحدة/حادثة مهمة، وقبل إطلاق رئيسي: هل يمكن لقائد جديد تحديد NEXT والأدلة والـblockers والصلاحيات من المستودع وحده؟ إذا لا، افتح تحديث توثيق محددًا.

## 8. حزمة استعادة مختصرة لأي نافذة جديدة

انسخ هذا الموجه، ثم أرفق أحدث لقطة من 14/04 عند الإمكان:

> **استأنف قيادة Dueli من المستودعات الحية، لا من الذاكرة.** دورك Lead Technical Architect + Project Lead + AI Engineering Orchestrator + Merge Owner؛ المالك صاحب القرار النهائي، وقائد التخطيط يملك تنظيم الخطة، LOCAL ينفذ فقط، وREMOTE يراجع مستقلًا فقط. ابدأ بقراءة [نظام استمرارية القيادة](19-LEADERSHIP-CONTINUITY-SYSTEM.md)، ثم 14 و04 و08 و10 و11 والمواصفة المرتبطة، واقرأ AGENTS.md وWORKLOG.md وPLAN-STATUS.md والوثائق الحاكمة ذات الصلة في CODE. تحقق من CODE main وPLAN main والـPRs/branches/reviews/checks والـruns الحية قبل اختيار NEXT؛ 14 وحده مصدر ترتيب العمل وCanonical NEXT. لا تعاود تكليف PR نشطة ولا تفتح عملًا مغلقًا دون عيب جديد مثبت. طبق Protocol 10: LOCAL أخضر → تحقق GitHub exact HEAD/BASE/CI → REMOTE APPROVE على exact HEAD → تحقق ومزج expected_head_sha → Quality وDeploy على actual merge SHA نفسه → تحديث الخطة عبر PR. إذا تعذرت الأدوات، لا تدّعِ التحقق ولا تدمج؛ اطلب أدلة قابلة للتحقق ووسمها REPORTED/NOT VERIFIED. ألزم كل تقرير LOCAL بملخص استعادة القيادة (§4)، وافصل MERGED عن DEPLOYED وPROD VERIFIED وACCEPTED. ابدأ بإرسال تقرير استئناف قصير: CODE MAIN SHA، PLAN MAIN SHA، PR النشطة، الأدلة المؤكدة، المجهول، وCanonical NEXT.

## 9. معيار نجاح النظام

يعد نظام الاستمرارية عاملًا عندما يستطيع قائد بديل، دون الاعتماد على المحادثة السابقة، أن:
- يحدد الأدوار وحدود الصلاحية.
- يعثر على أحدث CODE/PLAN SHA وحالة PR النشطة.
- يحدد NEXT من 14 ويعرف ما لا يجوز إعادة فتحه.
- يميّز بين مراجعة/دمج/بوابات نشر/قبول إنتاجي.
- يتعامل بأمان مع انقطاع الأدوات أو غياب المالك.
- يستعيد الدروس السابقة من سجل قابل للربط بالأدلة، ويحدّث الوثائق عبر PR بدل ترك المعرفة في المحادثة.
